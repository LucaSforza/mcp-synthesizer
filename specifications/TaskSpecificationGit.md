# Task Specification: Persist Successful Synthesis Results to Git

## Goal

Implement Git persistence for successful synthesis runs.

After a synthesis completes successfully, the system must automatically:

1. Create a dedicated Git branch for that synthesis.
2. Commit all generated artifacts.
3. Push the branch to the remote repository.
4. Return the repository to its original state so the next synthesis can run safely.

The implementation must use the Rust `git2` crate exclusively for Git operations.

---

# Motivation

Every synthesis run represents a potentially valuable implementation candidate.

We want:

* Complete reproducibility.
* Permanent storage of synthesis outputs.
* Easy comparison between different models.
* Easy comparison between different seeds.
* Isolation of synthesis attempts.

Each successful synthesis should therefore be stored on its own Git branch.

---

# Branch Naming

Create a branch using the following format:

```text
{model_name}-{iteration}-{seed}
```

Examples:

```text
qwen3-solidity-27B-Q6_K-15-104
Qwen3-Coder-Next-APEX-I-Compact-3-42
```

The values come from the synthesis job metadata:

| Field      | Source                      |
| ---------- | --------------------------- |
| model_name | Redis job key               |
| iteration  | Current synthesis iteration |
| seed       | Redis job seed              |

---

# Execution Point

This functionality should run only after a synthesis has completed successfully.

In queue_controller terminology this means:

```text
check_succeeded_full() == true
```

If the synthesis failed, no Git operations should be performed.

---

# Repository State Management

Before any Git operation:

1. Detect the currently checked-out branch.
2. Store its name.
3. Use it later to restore the repository state.

Example:

```text
master
```

or

```text
main
```

The implementation must not assume either branch name.

Always detect it dynamically.

---

# Branch Creation Workflow

## Step 1

Open the repository using git2.

Repository root should be the project directory currently being synthesized.

Example:

```text
<project-root>/<project-name>
```

---

## Step 2

Read current HEAD.

The new branch must be created from the current HEAD commit.

Pseudo-code:

```text
HEAD -> current_commit
create_branch(branch_name, current_commit)
```

---

## Step 3

Checkout the newly created branch.

After checkout:

```text
HEAD -> synthesis branch
```

---

# Branch Conflict Handling

The branch name may already exist.

Supported strategies:

## Initial Implementation

Fail immediately.

Example error:

```text
Branch already exists:
qwen3-solidity-27B-Q6_K-15-104
```

No commit or push should occur.

---

## TODO

Future configurable strategies:

```text
Fail
Overwrite
Reuse Existing
Append Timestamp
```

---

# Files To Commit

The commit must include:

## Modified Files

All tracked files modified by the synthesis.

---

## New Files

All newly generated files.

---

## Claude Conversation Output

The conversation JSON generated by queue_controller.

Example:

```text
qwen3-solidity-27B-Q6_K_15.json
```

This file is considered part of the synthesis result and must always be committed.

---

## Deleted Files

Deleted files should also be staged.

Equivalent behavior to:

```bash
git add -A
```

---

# Commit Creation

Create a commit after staging all changes.

The commit message must be configurable.

Example:

```text
Synthesis: qwen3-solidity-27B-Q6_K iteration 15 seed 104
```

The exact message format is provided by the caller.

---

# Push Workflow

After commit creation:

## Step 1

Push the newly created branch to origin.

Equivalent behavior:

```bash
git push origin branch_name
```

---

## Step 2

Configure upstream tracking.

Equivalent behavior:

```bash
git push --set-upstream origin branch_name
```

After completion:

```text
local branch tracks origin/branch_name
```

---

# Return To Original Branch

After a successful push:

1. Checkout the branch that was active before synthesis persistence began.
2. Verify checkout succeeded.

Example:

```text
checkout(main)
```

or

```text
checkout(master)
```

depending on the original state.

The repository must be left ready for the next synthesis run.

---

# Failure Handling

Every Git operation must be validated.

Operations requiring explicit error handling:

* repository open
* HEAD lookup
* branch creation
* branch checkout
* index update
* staging
* commit creation
* remote lookup
* authentication
* push
* upstream configuration
* checkout back to original branch

Errors must include contextual information.

Example:

```text
Failed to create synthesis branch:
qwen3-solidity-27B-Q6_K-15-104
```

rather than:

```text
Git error
```

---

# Logging

Use the project's existing logging style.

Example:

```text
[DEBUG] Creating synthesis branch qwen3-solidity-27B-Q6_K-15-104
[DEBUG] Staging repository changes
[DEBUG] Creating commit
[DEBUG] Pushing branch to origin
[DEBUG] Returning to branch main
```

All major Git operations should emit logs.

---

# Suggested API

Create a reusable component.

Example:

```rust
pub struct GitPersistence {
    repository: Repository,
}
```

Suggested entrypoint:

```rust
pub fn persist_synthesis(
    &self,
    model_name: &str,
    iteration: u64,
    seed: u64,
    commit_message: &str,
) -> anyhow::Result<()>
```

This keeps Git logic isolated from queue_controller.

---

# Success Criteria

The task is complete when:

1. A successful synthesis creates a dedicated branch.
2. The branch is created from the current HEAD.
3. All repository changes are staged.
4. The Claude conversation JSON is committed.
5. A commit is created successfully.
6. The branch is pushed to origin.
7. Upstream tracking is configured.
8. The repository returns to the previously checked-out branch.
9. Any Git failure returns a meaningful error.
10. The implementation uses only the git2 crate for Git operations.
